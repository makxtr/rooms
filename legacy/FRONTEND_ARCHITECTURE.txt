## Tech Stack

**Frontend:**
- Vanilla JavaScript (ES6 modules)
- jQuery 3.2.1 (CDN)
- Custom template engine
- FastClick
- Phoenix Channels (WebSocket)

**Backend:**
- Phoenix Framework (Elixir)
- HEEX templates (server-side rendering)

## Application Flow

### 1. Initial Page Load

**URL:** `http://localhost:4000/`

**What happens:**
1. Phoenix serves `root.html.heex` with `home.html.heex` content
2. Browser loads CSS and executes `app.js`
3. `app.js` dynamically imports all modules sequentially
4. After modules loaded, app fetches current session

**API Request:**
```
GET /api/sessions/me
Response: {
  session_id: "abc123",
  nickname: "User",
  status: "Hello",
  rand_nickname: true,
  user_id: null,
  provider_id: null,
  ignores: [[], {}],
  subscriptions: [],
  rooms: [],
  recent_rooms: [],
  talkrooms: { version: 39, whatsnew: "..." }
}
```

**Result:**
- `Me` object populated with session data
- Hash router checks URL and routes to appropriate view
- If hash is empty (`#`), shows hall (About page)

### 2. Entering Hall (Explore Mode)

**URL:** `http://localhost:4000/#` or `http://localhost:4000/#+`

**What happens:**
1. Router matches `/^$|^\+$/` patterns
2. Triggers `Rooms.explore()` or `Rooms.enter() + Rooms.explore()`
3. Shows `.hall` element with room lists

**UI Shows:**
- Recent rooms list (from `Me.recent_rooms`)
- My rooms list (from `Me.rooms`)
- Create room button
- Shuffle (random room) button

**No API calls** - uses data from `/api/sessions/me`

### 3. Creating New Room

**User Action:** Click "Create room" button

**API Request:**
```
POST /api/rooms
Response: { hash: "xyz789", topic: "#xyz789", ... }
```

**What happens:**
1. `Rooms.create()` called
2. POST request creates new room
3. Router redirects to `#xyz789`
4. Triggers room enter flow (see below)

### 4. Shuffle (Random Room)

**User Action:** Click shuffle button

**API Request:**
```
POST /api/rooms/search
Response: { hash: "random123", topic: "#random123", ... }
```

**What happens:**
1. `Rooms.shuffle()` called
2. Backend finds available room to join
3. Router redirects to `#random123`
4. Triggers room enter flow

**On Error (404):**
- Shows "No rooms available" message
- User stays in hall

### 5. Entering Room

**URL:** `http://localhost:4000/#roomhash`

**What happens:**
1. Router matches `/^[\w\-+]{3,}$/` pattern
2. Calls `Rooms.select(hash)`
3. If room not in `Rooms.byHash`, creates new Room object
4. Calls `room.enter()`

**API Request:**
```
POST /api/rooms/:hash/enter
Response: {
  room: { room_id: 123, hash: "roomhash", topic: "Room Name", level: 0, ... },
  role: { user_id: 456, nickname: "User", status: "Hello", level: 0, ... },
  subscription: { subscription_id: 789, ... },
  roles_online: [{ user_id: 1, nickname: "User1", ... }, ...],
  roles_waiting: []
}
```

**What happens after successful enter:**
1. Room state set to "ready"
2. `Rooms.selected` = current room
3. Phoenix Channel joined: `room:roomhash`
4. Triggers `Rooms.on("selected.ready")` event
5. UI switches from hall to room view

**WebSocket Connection:**
- Joins Phoenix channel `room:roomhash`
- Sends join params: `{ nickname, user_id }`
- Listens for real-time events

### 6. Room Denied/Locked (403)

**API Response:**
```
HTTP 403
{
  room: { level: 50, ... },
  role: { level: 0, banned_until: "2024-01-01", ... }
}
```

**What happens:**
1. Room state set to "locked" or "closed"
2. Triggers `Rooms.on("selected.denied")` event
3. Shows lock/ban screen instead of chat
4. User cannot send messages

**Cases:**
- `level: 80` - Room closed (deleted by admin)
- `level: 50` + user banned - Shows ban duration
- `level: 10` + user level < 10 - Room is private

### 7. Room Not Found (404)

**API Response:**
```
HTTP 404
```

**What happens:**
1. Room state set to "lost" or "deleted"
2. Shows "Room not found" message
3. Suggests creating new room or returning to hall

### 8. Loading Messages

**Load scenarios:**

1. **Initial load** - Room entered
   - Messages loaded via **REST API** after joining channel
   - Separate API call: `GET /api/messages?room_hash=abc&limit=50`
   - Returns last 50 messages in ascending order (oldest first)
   - Code: `talk.js:501` - `Talk.loadRecent()`

2. **Load older messages** - User scrolls to top (currently uses legacy code)
   - **REST API Request:**
   ```
   GET /api/messages?room_id=123&before_id=999&limit=150
   Response: [
     {
       message_id: 998,
       user_id: 456,
       nickname: "User",
       content: "Hello",
       created: "2024-01-01T12:00:00Z",
       recipient_user_id: null,
       ...
     },
     ...
   ]
   ```
   - Called via `Rest.messages.get()` in `talk.js:422`

3. **Date picker** - User selects specific date
   - **REST API Request:**
   ```
   GET /api/messages?room_id=123&created[>]=2024-01-01T00:00:00Z&limit=150
   ```
   - Loads messages from selected date forward

### 9. Sending Message

**User Action:** Type message and press Enter

**WebSocket Request:**
```javascript
// Client sends via Phoenix Channel
PhoenixSocket.sendMessage("Hello world")
// Internally calls:
currentChannel.push("new_message", { body: "Hello world" })
```

**What happens:**
1. Message sent via **WebSocket** channel push (`user_socket.js:134`)
2. Server receives, saves to DB, and broadcasts to all room members
3. All connected clients receive `new_message` event via WebSocket
4. Message appears in chat instantly for all users

**WebSocket Event Received by all clients:**
```javascript
{
  event: "new_message",
  payload: {
    message_id: 1001,
    user_id: 456,
    nickname: "User",
    body: "Hello world",
    timestamp: "2024-01-01T12:01:00Z"
  }
}
```

**Code references:**
- Send: `reply.js:80` → `user_socket.js:130-138`
- Receive: `user_socket.js:67-79` → `room.js` (via events)

### 10. Real-Time Events (WebSocket)

**Connected to:** `ws://localhost:4000/sockets` → Channel `room:roomhash`

**Events received:**

1. **new_message** - New message in room
```javascript
{ message_id: 1001, user_id: 456, text: "Hello", ... }
```

2. **presence_state** - Initial online users list
```javascript
{ "user_123": { metas: [{ nickname: "User", status: "...", ... }] } }
```

3. **presence_diff** - User joined/left
```javascript
{
  joins: { "user_456": { metas: [...] } },
  leaves: { "user_789": { metas: [...] } }
}
```

4. **message_deleted** - Message removed
```javascript
{ message_id: 998 }
```

5. **user_updated** - User changed nickname/status
```javascript
{ user_id: 456, nickname: "NewName", status: "NewStatus" }
```

6. **room_updated** - Room settings changed
```javascript
{ topic: "New Topic", level: 10, ... }
```

### 11. Updating Profile

**User Action:** Open profile modal, change nickname/status

**API Request:**
```
PATCH /api/sessions/me
Body: { nickname: "NewName", status: "NewStatus" }
Response: { nickname: "NewName", status: "NewStatus", ... }
```

**What happens:**
1. Profile updated in database
2. Backend broadcasts `user_updated` via WebSocket to all rooms
3. All clients update user display in online lists and messages

### 12. Private Messages

**User Action:** Click username → Send private message

**Implementation:**
- Private messages sent via **WebSocket** (same as regular messages)
- UI shows reply form with recipient indicator
- Message text may include mentions like "@User Hello"

**What happens:**
1. Message sent via WebSocket `new_message` event
2. Server handles recipient logic (currently in development)
3. UI highlights private messages differently for sender/recipient
4. Code: `reply.js:264` - `Room.replyPrivate()`

### 13. Leaving Room

**User Action:** Click "Back to hall" OR navigate to `#` OR close tab

**What happens:**
1. `room.leave()` called
2. Phoenix Channel left
3. UI switches back to hall
4. WebSocket disconnects from room channel

**No API call** - just local cleanup

### 14. Moderation Actions (Level ≥ 50)

**Available when:** `room.myRole.level >= 50`

**Actions:**

1. **Delete message**
```
DELETE /api/messages/:id
```

2. **Ban user**
```
PATCH /api/rooms/:hash/roles/:user_id
Body: { banned_until: "2024-01-31T23:59:59Z" }
```

3. **Change user level**
```
PATCH /api/rooms/:hash/roles/:user_id
Body: { level: 30 }
```

## Important Notes

### CORS Requirements
- Frontend must be served from same origin as backend OR
- CORS must be configured if frontend on different port
- `127.0.0.1:4000` and `localhost:4000` are **different origins**
- Use `localhost:4000` consistently

### Session Management
- Session stored in cookie `_chats_key`
- Automatically included in all API requests
- Required for authentication

### Hybrid Architecture: REST + WebSocket

**Client maintains TWO simultaneous connections:**

1. **HTTP REST API** (`$.Rest()` via jQuery AJAX)
   - Used for: CRUD operations, one-time requests, data fetching
   - Stateless, request-response pattern
   - Session auth via cookies (`_chats_key`)

2. **WebSocket** (Phoenix Channels via `user_socket.js`)
   - Used for: Real-time bidirectional communication
   - Persistent connection, stays open entire session
   - Push notifications from server to client

**Why both?**
- REST is efficient for standard operations (no need to hold WebSocket)
- WebSocket enables instant updates without polling
- Separation of concerns: data operations vs real-time events

**Typical User Flow:**
```
1. Open page
   → HTTP GET /api/sessions/me (get user data)

2. Navigate to room
   → HTTP POST /api/rooms/:hash/enter (join room, get room data)
   → WebSocket joinRoom(roomId) (subscribe to real-time events)
   → HTTP GET /api/messages?room_hash=abc&limit=50 (load recent messages)

3. User scrolls up to load older messages (future feature)
   → HTTP GET /api/messages?room_hash=abc&before=timestamp&limit=150

4. Send message
   → WebSocket push "new_message" (send message via channel)
   → Server saves to DB and broadcasts to all clients in room
   → All users receive message instantly via WebSocket

5. Another user joins room
   → WebSocket "presence_diff" event (instant notification to all)

6. Update profile
   → HTTP PATCH /api/sessions/me (update in DB)
   → Server broadcasts via WebSocket "user_updated" to all rooms
```

**Connection lifecycle:**
- WebSocket connects once on app.js load: `socket.connect()`
- HTTP requests made as needed throughout session
- Both share same session cookie for authentication
- WebSocket reconnects automatically on disconnect

**Data flow patterns:**

| Operation | Method | Reason |
|-----------|--------|--------|
| Get session info | REST | One-time data fetch on page load |
| Get room info | REST | Room metadata and permissions |
| Join room | REST + WS | REST for auth/data, WS for real-time channel |
| Initial messages | WebSocket | Sent by server on channel join |
| Load older messages | REST | Paginated historical data (scroll up) |
| Send message | WebSocket | Real-time delivery to all users |
| Receive message | WebSocket | Real-time broadcast to all |
| User presence | WebSocket | Live online/offline status |
| Update profile | REST | Persist changes to DB |
| Show profile change | WebSocket | Notify all rooms instantly |
| Edit message | REST | Update in DB with validation |
| Delete message | REST | Moderation action |

### Room States
- `null` - Not entered yet
- `"ready"` - Successfully entered, can chat
- `"locked"` - Access denied (banned or insufficient level)
- `"closed"` - Room deleted/closed
- `"lost"` - Room not found (404)
- `"deleted"` - Room was deleted
- `"error"` - Server error

### Message Visibility
Messages filtered based on:
- User ignore list (`Me.ignores`)
- Private message recipient (`recipient_user_id`)
- Filter mode (all messages / mentions only)
- Moderator status (moderators see all)
